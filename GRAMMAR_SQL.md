# GRAMMAR_SQL.md

Grammar of the SQL subset of Module 3, in EBNF (ISO 14977 style, as in GRAMMAR.md: `,` is
sequence, `|` is choice, `{ }` is zero or more, `[ ]` is optional, quoted text is a terminal).
Keywords are written in capitals and match in any case. Every rule name below is a method of the
same name in `sqlfront/parser.py`, and everything the parser accepts is generated by this grammar.

## 1. The grammar

### 1.1 Statements

```ebnf
script        = [ statement ] , { ";" , [ statement ] } ;

statement     = create | insert | query ;

create        = CREATE , TABLE , IDENT , "(" , coldef , { "," , coldef } , ")" ;
coldef        = IDENT , ( INT | VARCHAR , "(" , INTEGER , ")" ) ;

insert        = INSERT , INTO , IDENT , VALUES , "(" , literal , { "," , literal } , ")" ;
literal       = INTEGER | STRING ;
```

### 1.2 Queries

```ebnf
query         = select_block , { setop , select_block } ;
setop         = UNION , [ ALL ] | INTERSECT | EXCEPT ;

select_block  = SELECT , [ DISTINCT ] , select_list ,
                FROM , from_list ,
                [ WHERE , condition ] ,
                [ GROUP , BY , col_list , [ HAVING , condition ] ] ,
                [ ORDER , BY , sort_list ] ,
                [ LIMIT , INTEGER ]
              | "(" , query , ")" ;

select_list   = "*" | select_item , { "," , select_item } ;
select_item   = ( column | aggregate ) , [ AS , IDENT ] ;
aggregate     = ( COUNT | SUM | AVG | MIN | MAX ) , "(" , ( column | "*" ) , ")" ;

from_list     = table_ref , { "," , table_ref | JOIN , table_ref , ON , condition } ;
table_ref     = IDENT , [ [ AS ] , IDENT ]
              | "(" , query , ")" , [ AS ] , IDENT ;

col_list      = column , { "," , column } ;
sort_list     = sort_item , { "," , sort_item } ;
sort_item     = column , [ ASC | DESC ] ;
```

### 1.3 Conditions

```ebnf
condition     = and_condition , { OR , and_condition } ;
and_condition = not_condition , { AND , not_condition } ;
not_condition = NOT , not_condition
              | "(" , condition , ")"
              | comparison ;
comparison    = operand , COMP_OP , operand ;
operand       = column | INTEGER | STRING | aggregate ;
column        = IDENT , [ "." , IDENT ] ;
```

### 1.4 Tokens

```ebnf
IDENT    = ( letter | "_" ) , { letter | digit | "_" } ;      (* and not a keyword *)
INTEGER  = [ "+" | "-" ] , digit , { digit } ;
STRING   = "'" , { character - "'" | "''" } , "'" ;           (* '' inside a string is one quote *)
COMP_OP  = "=" | "<>" | "<" | "<=" | ">" | ">=" ;
```

Punctuation tokens are `( ) , . ; *`. Whitespace separates tokens. `--` begins a comment that
runs to the end of the line. The scanner (`sqlfront/lexer.py`) reads one character at a time:

- **Keywords are case insensitive**, identifiers are case sensitive. A word is looked up in the
  keyword table in upper case; if it is there it is a keyword, otherwise it is an identifier kept
  exactly as written. `SeLeCt` is the keyword SELECT; `Emp` and `emp` are two tables.
- **Maximal munch.** After `<` the scanner looks one character ahead and produces `<=` or `<>`
  if it can, otherwise `<`. After `>` it produces `>=` if it can. So `a<>b` is three tokens.
- **Signed integers.** A `+` or `-` directly followed by a digit begins an INTEGER. The language
  has no arithmetic, so `age>-5` can only mean `age`, `>`, `-5`. `--` is checked first, so a
  comment is never read as two signs.
- An INTEGER must fit a 4-byte signed INT. `12abc` and `1.5` are lexical errors, not a number
  followed by something else.
- Every token records its line and column, which is where every error message gets its position.

The keywords, all reserved: `SELECT DISTINCT FROM WHERE GROUP BY HAVING ORDER ASC DESC LIMIT
UNION ALL INTERSECT EXCEPT JOIN ON AS AND OR NOT CREATE TABLE INSERT INTO VALUES INT VARCHAR
COUNT SUM AVG MIN MAX`.

## 2. Precedence and associativity

Each level is one grammar rule. A level is left associative because its rule is
`first , { operator , next }`: the parser reads the first operand, then wraps what it has with
each following operator in turn. A level binds tighter than another because its rule is called
by the other. The parser methods contain no precedence comparisons.

Conditions, loosest first:

| Level | Operator | Associativity | Rule that enforces it |
|---|---|---|---|
| 1 (loosest) | `OR` | left | `condition = and_condition , { OR , and_condition }` |
| 2 | `AND` | left | `and_condition = not_condition , { AND , not_condition }` |
| 3 | `NOT` | prefix, nests to the right | `not_condition = NOT , not_condition` |
| 4 (tightest) | comparison, `( condition )` | none: a comparison has exactly two operands | `comparison`, `not_condition` |

So `a = 1 OR b = 2 AND NOT c = 3` is `a = 1 OR (b = 2 AND (NOT c = 3))`, and
`NOT a = 1 AND b = 2` is `(NOT a = 1) AND b = 2`. Comparisons do not chain: `a < b < c` is a
syntax error, because after `a < b` the grammar has no rule that continues with `<`.

Set operators:

| Level | Operators | Associativity | Rule |
|---|---|---|---|
| 1 | `UNION`, `UNION ALL`, `INTERSECT`, `EXCEPT` | left | `query = select_block , { setop , select_block }` |
| 2 | `( query )` | | `select_block` |

All four share one level, so `A UNION B EXCEPT C` is `(A UNION B) EXCEPT C` and
`A EXCEPT B INTERSECT C` is `(A EXCEPT B) INTERSECT C`. Standard SQL gives INTERSECT a higher
precedence; this subset does not, by specification. Parentheses give the other grouping:
`A UNION (B EXCEPT C)`.

The FROM clause:

| Level | Operators | Associativity | Rule |
|---|---|---|---|
| 1 | `,` and `JOIN ... ON` | left | `from_list = table_ref , { "," , table_ref \| JOIN , table_ref , ON , condition }` |

`FROM A, B JOIN C ON c` is `(A cross B) join C`.

## 3. Where this grammar differs from the sketch in the specification, and why

1. **An aggregate is an operand.** The sketch has `operand ::= column | int | string`, but
   Section 5.4 of the specification writes `HAVING COUNT(*) > 5`, and required case 7 demands an
   *aggregate* error for an aggregate in WHERE, not a syntax error. Both need the parser to
   accept an aggregate wherever an operand may stand. Whether it is allowed there is decided
   later, by the clause it is in.
2. **Comma and JOIN may be mixed.** The sketch's `from_list` is either a comma list or a JOIN
   chain. Here each further table is attached by either one. The language is a superset, both
   forms of the sketch are still accepted unchanged, and the rule is one loop instead of a
   choice the parser would have to make after reading the first table.
3. **`AS` is optional before a table alias.** The sketch writes `ident [ AS ident ]`, but every
   example in Section 5 writes `Emp e` without it. Both are accepted. In the select list `AS`
   stays required, because there a second bare name is far more likely a missing comma.
4. **`sort_list` and `col_list` are spelled out.** `sort_item = column [ ASC | DESC ]`, with ASC
   the default.
5. **A script level.** `script` allows empty statements and a final semicolon, so `;;` and a
   trailing `;` are not errors.
6. **Literals in INSERT** are `INTEGER | STRING`, the only two types there are.

One thing is kept exactly as the sketch has it, though standard SQL differs: `ORDER BY` and
`LIMIT` belong to a `select_block`. In `A UNION B ORDER BY x` they apply to `B`. To order a
whole union, write it as a subquery: `SELECT ... FROM (A UNION B) AS t ORDER BY ...`.

## 4. Parsing strategy

Hand-written recursive descent, one method per rule, one token of lookahead (`cur()`), no
backtracking, no parser generator, no regular expressions. The grammar is LL(1); the places
where a choice is made, and the token that decides it:

| Choice | Decided by |
|---|---|
| `statement` | `CREATE`, `INSERT`, or `SELECT` / `(` |
| `select_block` | `SELECT` or `(` |
| `select_list` | `*` or anything else |
| `select_item`, `operand` | an aggregate keyword, an IDENT, a literal |
| `table_ref` | `(` or an IDENT; then `AS` or an IDENT for the alias |
| `from_list` loop | `,` or `JOIN` |
| `not_condition` | `NOT`, `(`, or an operand |

`(` in `not_condition` always opens a parenthesised condition, because no operand starts with
`(`. That is what keeps conditions LL(1); it would stop being true if subqueries were allowed
as operands.

**Left recursion** is removed the same way as in Bonus Project 1. `query = query setop
select_block` would call itself without consuming a token, so it is written
`select_block { setop select_block }` and the loop rebuilds the left-leaning tree by hand:
`left = SetOp(op, left, right)`. The same for `condition`, `and_condition` and `from_list`.

**Errors.** Panic mode: the first error raises and parsing stops. A syntax error says what was
expected and what was found, with the position of the token that was found:
`error: syntax: expected a column, a number or a string, found end of input at line 2, column 19`.
A keyword used as a name is reported as such (`'select' is a reserved word`).
