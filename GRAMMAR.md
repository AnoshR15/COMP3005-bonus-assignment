# GRAMMAR.md

Grammar of the relational algebra language for Bonus Project 1, in EBNF (ISO 14977 style: `,` is
sequence, `|` is choice, `{ }` is zero or more, `[ ]` is optional, quoted text is a terminal,
`(* *)` is a comment). Everything the parser accepts is generated by this grammar, and every rule
name below is a method of the same name in `source/parser.py`.

## 1. The grammar

### 1.1 Queries

```ebnf
query         = expr ;

expr          = set_expr ;
set_expr      = product_expr , { ( "union" | "intersect" | "minus" ) , product_expr } ;
product_expr  = join_expr , { "times" , join_expr } ;
join_expr     = primary , { "join" , "[" , condition , "]" , primary } ;
primary       = "(" , expr , ")"
              | "select" , "[" , condition , "]" , "(" , expr , ")"
              | "project" , "[" , attr_list , "]" , "(" , expr , ")"
              | "rename" , "[" , IDENT , "]" , "(" , expr , ")"
              | "distinct" , "(" , expr , ")"
              | IDENT ;                                  (* a relation name *)
attr_list     = attr , { "," , attr } ;                  (* at least one attribute *)

condition     = or_condition ;
or_condition  = and_condition , { "or" , and_condition } ;
and_condition = not_condition , { "and" , not_condition } ;
not_condition = "not" , not_condition
              | "(" , condition , ")"
              | comparison ;
comparison    = operand , COMP_OP , operand ;
operand       = NUMBER | STRING | attr ;
attr          = IDENT , [ "." , IDENT ] ;                (* Name, or Relation.Name *)
```

`condition` is also a start symbol of its own. `Parser.parse_condition` reads `condition` followed
by the end of the input, which is how the other modules of the database system turn a condition
string such as `R.b = S.b and R.a > 500` into a tree (`source/condition.py`).

### 1.2 Tokens

```ebnf
IDENT   = ( letter | "_" ) , { letter | digit | "_" } ;
NUMBER  = [ "-" ] , digit , { digit } , [ "." , digit , { digit } ] ;
STRING  = "'" , { character - "'" | "''" } , "'" ;      (* '' inside a string is one quote *)
COMP_OP = "=" | "!=" | "<>" | "<" | "<=" | ">" | ">=" ;
```

The punctuation tokens are `[ ] ( ) , .`. Whitespace separates tokens and is otherwise ignored;
`//` begins a comment that runs to the end of the line. The scanner (`source/tokenizer.py`) reads
one character at a time and applies maximal munch: after `>` it looks at the next character and
produces `>=` if it is `=`, otherwise `>`. A `-` directly followed by a digit begins a NUMBER,
since the language has no subtraction, so `Age>-30` scans as `Age`, `>`, `-30`. The words
`select project rename distinct union intersect minus times join and or not` are scanned as IDENT tokens
like any other word; the parser gives them meaning by position (section 6).

### 1.3 Relation definition files

```ebnf
file        = { definition } ;
definition  = IDENT , "(" , IDENT , { "," , IDENT } , ")" , "=" , "{" , NEWLINE ,
              { tuple , NEWLINE } , "}" ;
tuple       = value , { "," , value } ;
value       = NUMBER | STRING | BARE ;
BARE        = bare_char , { bare_char } ;               (* any character except , ' ( ) space *)
```

One tuple per line. A value that scans as a NUMBER is a number, a quoted value is a string, and
any other bare text is a string (`E1`, `John`, `D1`). A string that contains a comma, space,
parenthesis or quote must be quoted. `//` comments and blank lines are ignored. A relation is a
bag, so a tuple written twice is stored twice. Each attribute's type, number or string, is taken from its
values; a column may not mix the two, and a relation needs at least one tuple.

## 2. Precedence and associativity

Expression operators, loosest first. Each level is one grammar rule, and the `{ ... }` repetition
in that rule is what makes the level left associative: the parser reads the first operand, then
wraps it with each following operator in turn.

| Level | Operators | Associativity | Rule that enforces it |
|---|---|---|---|
| 1 (loosest) | `union`, `intersect`, `minus` | left | `set_expr = product_expr , { op , product_expr }` |
| 2 | `times` | left | `product_expr = join_expr , { "times" , join_expr }` |
| 3 | `join[c]` | left | `join_expr = primary , { "join" , "[" , condition , "]" , primary }` |
| 4 (tightest) | `select[c](..)`, `project[..](..)`, `rename[..](..)`, `distinct(..)`, `( expr )` | none needed: fully bracketed | `primary` |

Condition operators:

| Level | Operator | Associativity | Rule |
|---|---|---|---|
| 1 (loosest) | `or` | left | `or_condition = and_condition , { "or" , and_condition }` |
| 2 | `and` | left | `and_condition = not_condition , { "and" , not_condition }` |
| 3 | `not` | prefix, nests to the right (`not not x`) | `not_condition = "not" , not_condition` |
| 4 (tightest) | comparison, `( condition )` | none needed | `comparison`, `not_condition` |

The decisions these tables encode:

- `A union B minus C` means `(A union B) minus C`, and `A minus B minus C` means
  `(A minus B) minus C`. All three set operators share one level and associate to the left, so a
  chain of set operators always reads left to right. SQL gives `INTERSECT` a higher precedence;
  here `A union B intersect C` is `(A union B) intersect C`, which is simpler to read and explain.
- `times` binds tighter than the set operators, as a product does against a sum. `join` binds
  tighter than `times`, so `A times B join[c] C` is `A times (B join[c] C)`.
- `not (a=1 and b=2) or c>3` is `(not (a=1 and b=2)) or (c>3)`, and `a=1 and b=2 or c=3` is
  `(a=1 and b=2) or c=3`.
- Parentheses override every level: `(A union B) minus (C intersect D)`.

The parser contains no special cases for any of this. `A union B minus C` prints as
`Minus(Union(A, B), C)` because `set_expr` parsed `A`, looped once for `union B`, then once more
for `minus C`, wrapping the previous result each time.

## 3. Ambiguity demonstration

The naive grammar

```text
Expr ::= Expr "union" Expr
       | Expr "minus" Expr
       | "(" Expr ")"
       | IDENT
```

generates `A union B minus C` with two different parse trees. Every interior node is the
nonterminal `Expr`; the leaves are terminals.

Tree 1, root production `Expr ::= Expr "minus" Expr`:

```text
                   Expr
          ___________|___________
         |           |           |
        Expr      "minus"       Expr
     ____|____                   |
    |    |    |                IDENT
  Expr "union" Expr              C
   |           |
 IDENT       IDENT
   A           B
```

Tree 2, root production `Expr ::= Expr "union" Expr`:

```text
                   Expr
          ___________|___________
         |           |           |
        Expr      "union"       Expr
         |                   ____|____
       IDENT                |    |    |
         A                Expr "minus" Expr
                           |           |
                         IDENT       IDENT
                           B           C
```

Tree 1 means `(A union B) minus C`. Tree 2 means `A union (B minus C)`.

A concrete instance on which they differ: `A = {1}`, `B = {2}`, `C = {1}`.

| Tree | Evaluation | Result |
|---|---|---|
| 1 | `A union B = {1, 2}`, then `{1, 2} minus C = {1, 2} minus {1}` | `{2}` |
| 2 | `B minus C = {2} minus {1} = {2}`, then `A union {2}` | `{1, 2}` |

The stratified grammar that removes the ambiguity:

```text
Expr ::= Term { ("union" | "minus") Term }
Term ::= "(" Expr ")" | IDENT
```

An operand of `union` or `minus` is now a `Term`, and a `Term` is only an identifier or a
parenthesised expression, so `B minus C` can no longer be the right operand of `union` unless it
is written `(B minus C)`. The repetition consumes operators from left to right and wraps what it
already has, so the only tree for `A union B minus C` is tree 1, `(A union B) minus C`. The full
grammar in section 1 is the same construction with more levels: `set_expr` over `product_expr`
over `join_expr` over `primary`.

The same rule settles case 11. The grammar forces `A minus B minus C` to mean
`(A minus B) minus C`. With `A = {1, 2, 3}`, `B = {1}`, `C = {2}`:
`(A minus B) minus C = {2, 3} minus {2} = {3}`, whereas the other grouping
`A minus (B minus C) = A minus {1} = {2, 3}`. Both instances are executed by
`tests/test_parser.py` (cases 10 and 11), which check the printed tree and both results.

## 4. Parsing strategy

The parser is hand-written recursive descent: one method per grammar rule, one token of
lookahead (`cur()`), no backtracking. The grammar is LL(1), meaning the current token alone
decides which alternative to take at every choice point (`(`, `select`, `project`, `rename`,
`distinct` or an identifier in `primary`; `not`, `(` or an operand in `not_condition`), so the parser stays short,
the rule methods build the tree directly, and every error can say what was expected and at which
position (the scanner records a position on every token).

**Left recursion.** A rule of the form
`set_expr = set_expr , "union" , product_expr | product_expr` is left recursive: the method for
`set_expr` would begin by calling `set_expr` again without consuming a token, and recurse until
the stack overflows. Recursive descent cannot use such rules. Every left-associative level in this
grammar is therefore written with repetition instead, and that is the exact place the left
recursion was removed:

| Left-recursive form, not used | Form used, and where it lives |
|---|---|
| `set_expr = set_expr , op , product_expr` | `set_expr = product_expr , { op , product_expr }`; the `while` loop in `Parser.set_expr` |
| `product_expr = product_expr , "times" , join_expr` | `product_expr = join_expr , { "times" , join_expr }`; `Parser.product_expr` |
| `join_expr = join_expr , "join" , ... , primary` | `join_expr = primary , { "join" , ... , primary }`; `Parser.join_expr` |
| `or_condition = or_condition , "or" , and_condition` | `or_condition = and_condition , { "or" , and_condition }`; `Parser.or_condition` |
| `and_condition = and_condition , "and" , not_condition` | `and_condition = not_condition , { "and" , not_condition }`; `Parser.and_condition` |

Each loop rebuilds the left-associative tree by hand, `left = BinaryOp(op, left, right)` after
every iteration, so the tree a left-recursive grammar would have produced is still the tree we get.
Right recursion is harmless to recursive descent and is used once, for `not`:
`not_condition = "not" , not_condition`.

AI assistance was used to draft code and documents. Where it was wrong, with the details in
`DESIGN_LOG.md`:

1. The first draft of this document claimed that any keyword can be used as an attribute name.
   Testing the sentence showed `select[not=3](R)` is rejected, because `not_condition` tries the
   keyword first. Section 6 is the corrected rule.
2. The join it wrote built the whole cross product in memory and then selected from it. It ran
   out of memory at 4000 x 4000 tuples, and the report needs 64000 x 64000.
3. It resolved attribute names and checked operand types once per row instead of once against the
   schema, so an unknown attribute in a selection over an empty relation produced an empty result
   instead of an error, and a type error on the right of an `and` was never reported.

## 6. Keyword-spelled identifiers (case 8)

The scanner does not reserve keywords: `union`, `select`, `and` and the rest are IDENT tokens
like any other word. The parser reads a word as an operator only in a position where the grammar
allows an operator, and as a name everywhere else. In `select[union=3](R)` the word `union` sits
where `operand` expects an attribute, so it is the attribute named `union`, and the tree prints as
`Select(cond=Eq(Attr(union), Num(3)))`.

Two restrictions follow from the grammar, because in those positions the keyword is tried first:

- `not` at the start of a condition always begins a negation, so an attribute named `not` cannot
  be the left operand of a comparison.
- `select`, `project`, `rename` and `distinct` at the start of a primary always begin a unary
  operator, so a relation cannot be named `select`, `project`, `rename` or `distinct`.

Everything else works by position: `union union R` is the union of the relation named `union`
with `R`, and `select[and=1 or or=2](R)` compares attributes named `and` and `or`.

## 7. Other decisions the grammar leaves to the engine

- `project[Name, Name](R)` (case 24) is a schema error: "Duplicate attribute 'Name' in projection
  list". Allowing it would put two identical columns in the result and make every later
  unqualified reference to `Name` ambiguous.
- Tuple equality: two tuples are equal when they have the same arity and equal values position by
  position, numbers compared numerically (`30` and `30.0` are one value) and strings compared
  exactly, case-sensitively. This is `tuple_equal` in `source/operators.py`. Every stored row is
  put in canonical form first, so the identity test a set or dictionary performs is that definition.
- Relations are bags (changed for Project 2; Bonus Project 1 used sets). `select`, `project`,
  `rename`, `times` and `join` keep duplicates. `distinct(e)` removes them. `union`, `intersect`
  and `minus` are the set versions and return no duplicates; their bag versions exist in the tree
  and in JSON (`union_all`) but have no query syntax, because SQL is what will ask for them.
- Union compatibility is SQL's: the same number of attributes and the same type in each
  position. Names do not have to match (changed for Project 2; Bonus Project 1 required it).
- `<>` is accepted as another spelling of `!=`, because SQL conditions use it.
- An unqualified attribute name matches any relation in the schema. If it matches more than one
  column, it is a name error that asks for qualification.
- `A times B` names its attributes `A.x` and `B.y`. If the same qualified name would appear twice,
  as in `Emp times Emp`, it is a schema error; so is a `rename` that would give two attributes the
  same name.
