## 1. Capacity

By hand, from Section 3 of the specification: an empty page has 4088 bytes of free space and a
record of L bytes needs L + 4, so floor(4088 / (L + 4)) records fit.

| Schema | Record | L |
|---|---|---|
| a INT, b INT, c INT | 4 + 4 + 4 | 12 |
| a INT, b VARCHAR(20), c INT, b always 3 bytes | 4 + (2 + 3) + 4 | 13 |
| a INT, b VARCHAR(20), c INT, b of 2 to 9 bytes | 4 + (2 + 2…9) + 4 | 12 to 19 |
| k INT, pad VARCHAR(200), pad always 200 bytes | 4 + (2 + 200) | 206 |

20,000 rows were loaded into each and the slots on every data page counted.

| data | record length L, bytes (mean) | computed floor(4088 / (L + 4)) | measured, mean over full pages | fewest on a page | most on a page | data pages for 20,000 rows |
|---|---|---|---|---|---|---|
| all INT | 12 | 255 | 255 | 255 | 255 | 79 |
| short VARCHAR, every value 3 bytes | 13 | 240 | 240 | 240 | 240 | 84 |
| short VARCHAR, values of 2 to 9 bytes | 15.68 | 207 | 207.38 | 204 | 211 | 97 |
| VARCHAR(200), every value 200 bytes | 206 | 19 | 19 | 19 | 19 | 1053 |

**Fixed-length records: no difference.** 255, 240 and 19 on every full page, as computed. 240
for L = 13 is the figure given in the specification.

What the floor throws away is worth stating, because it is the real cost of a wide record. An
all-INT page ends with 4088 − 255 × 16 = 8 bytes unused, 0.2 percent. A VARCHAR(200) page ends
with 4088 − 19 × 210 = 98 bytes unused, 2.4 percent, and nothing can use them because every
record of that table needs 210.

**Variable-length records: 207.38 measured against 207 computed, and pages from 204 to 211.**
The hand formula has no single L to use, so it was given the mean, 15.68 bytes. Two things
separate it from the measurement.

1. *A page does not hold "mean" records.* It holds whatever arrived. A page that happened to get
   short names holds 211 rows, one that got long ones holds 204. The formula describes the
   average page and no actual page.
2. *The floor is applied once, to the mean, but the waste happens on every page.* Without the
   floor the formula gives 4088 / 19.68 = 207.72. Each real page stops when the next record does
   not fit, leaving a few bytes: 207.72 − 207.38 = 0.34 of a record, about 7 bytes a page. That
   is less than half of the smallest record (16 bytes with its slot), which is what first fit
   should achieve: a later short record is put into the gap a longer one could not use.

So the measurement lies between the floored formula and the unfloored one, and that is where it
should be.

## 2. Replacement policies

**The traces are my own.** No trace files were published with the specification, so I wrote

its one description, trace 3. They are in `traces/` as `trace1.txt` … `trace5.txt`, written by
`bench/m1_measure.py` with a fixed seed, so they are the same files on every run and every row
below can be reproduced by hand:

```
storage trace --file traces/trace2.txt --frames 64 --policy lru --json
{"policy": "lru", "frames": 64, "hits": 2998, "misses": 2002, "evictions": 1938, "reads": 2002, "writes": 0, "requests": 5000}
```

`traces/example.txt` is the six fetches of Section 5.3 and gives its totals at `--frames 3`.

Each trace is there for one reason. Trace 1 has no locality at all, so it shows what a pool

Trace 3 is the specification's repeated scan of a file larger than the pool. Trace 4 is a small
working set interrupted by long scans, the case where a scan pushes out pages that will be

### Trace 3 at B = 64

**LRU achieves 0 hits out of 800.** So does CLOCK. Both reach 90 percent (720 of 800) only at
B = 256, where the whole file fits and only the first pass misses.

The mechanism, in two sentences. The scan touches all 80 pages before it comes back to the
first, and LRU keeps the 64 touched most recently, so the page it evicts each time is the one
the scan will ask for soonest, 16 requests later. Every request is therefore a miss, at any B
below 80: 64 frames buy exactly what 4 frames buy.

CLOCK fails the same way for a related reason. Every page is loaded with its reference bit set
and never touched again before the hand comes round, so the hand clears a full circle of bits
and then evicts in loading order: first in, first out, which on a cyclic scan is the same order
as least recently used.

This is sequential flooding, and neither policy can avoid it, because both rank pages only by
how recently they were touched. A page that was touched once by a scan looks exactly as
valuable as a page that is touched constantly.

### Which policy I would ship

**CLOCK.**

- *It loses nothing where both fail.* Trace 3 is 0 percent under both at B ≤ 64.
- *It loses little elsewhere.* On the other four traces LRU is ahead in most rows by 0 to 2.6
  points; the largest gap is the hot-set
  trace at B = 64, 60.0 against 57.4 percent. On the uniform random trace CLOCK is ahead by a
  tenth of a point, which is noise.
- *It is cheaper on the path that matters.* A hit under CLOCK sets one bit in the frame it
  already has in hand. A hit under LRU has to move the frame in an ordering that every other
  fetch also changes. In this single-threaded program that is one assignment either way, but in
  a system with concurrent queries the LRU ordering is a structure every reader fights over, and
  hits are the common case one most wants to be free.

What I would not claim is that CLOCK is *good*. It is LRU's approximation with LRU's blind
spot. A policy that actually handles trace 3 has to know more than the last touch, such as the
time of the second-to-last one (section 4).

## 3. Scan cost

A table of 127,500 rows of three INTs: 500 data pages and one directory page, 501 pages in
`Big.db`. Scanned with `HeapFile.scan`, the scan `storage scan` uses, in a fresh process each
time.

| B | rows | page reads | hits | misses | evictions | writes | most pages pinned at once |
|---|---|---|---|---|---|---|---|
| 2 | 127500 | 502 | 1 | 502 | 500 | 0 | 2 |
| 8 | 127500 | 502 | 1 | 502 | 494 | 0 | 2 |
| 64 | 127500 | 502 | 1 | 502 | 438 | 0 | 2 |

**502 page reads at B = 2, 8 and 64.** 500 data pages, 1 directory page, and 1 page of the
catalog to find the table. The number neither falls nor rises with B.

It does not fall because a single scan never asks for the same data page twice, so there is
nothing for a larger pool to have kept. The one hit in each run is the catalog page, fetched a
second time to read the entry it has just been found to hold. Evictions fall as B grows (500,
494, 438) only because a larger pool has more empty frames to fill before it must evict; the
reads behind them are the same.

It does not rise because the scan pins at most two pages, in every run, so even B = 2 is enough
and no page is ever read twice for want of a frame.

The execution engine's `seqscan` reads 500 for the same table, not 501: it skips the directory
page (DESIGN_M1.md section 10).

## 4. Sources

- Ramakrishnan and Gehrke, *Database Management Systems*, ch. 9. The slotted page with a
  directory of (offset, length) slots, the heap file as a directory of pages, and the buffer
  manager's pin count and dirty bit are all from this chapter; so is the description of
  sequential flooding that section 2 reproduces.
- O'Neil, O'Neil and Weikum, *The LRU-K Page Replacement Algorithm for Database Disk Buffering*,
  SIGMOD 1993. Its starting point is the failure measured in section 2: LRU cannot tell a page
  that is touched often from one that was touched once, because it keeps only the last
  reference. LRU-K ranks by the K-th most recent reference instead. That is why the answer to
  "which would you ship" stops short of calling either policy good.
